## Purpose

This file is paste-ready copy for the Chrome Web Store (CWS) developer console submission form: the single-purpose statement, a permission-justification paragraph per permission, the content-script/injected-provider justification, and the draft listing copy. It is kept in-repo, not typed fresh into the console each time, so a resubmission after a rejection reuses language a reviewer has already seen rather than improvising new wording under time pressure. Whenever a permission, the content-script match list, or the single-purpose statement changes, update this file in the same change.

The D6 non-TLS decision was an open placeholder at S1; it is resolved (§3, narrow) and the paragraph below reflects the resolved manifest. Stage S7 produced the listing assets referenced in §5 (screenshots, promo tile) under `packages/extension/docs/listing-assets/`, generated by `packages/extension/scripts/capture-listing-screenshots.mjs` so the next person can regenerate them against a changed UI instead of retaking them by hand. What remains open past S7 is entirely operator decisions (D1 public-identity set, D2 category/final name, D5 privacy-policy URL going live) and the submission ceremony itself (S8), not more content for this file to draft.

## 1. Single-purpose statement

Paste into the CWS "Single purpose" field:

> XChain Wallet lets a user hold and move XChain Platform assets (Bitcoin, Dogecoin, Litecoin, and their XChain-issued tokens) self-custodially from within the browser, and sign XChain actions on behalf of dApps the user explicitly connects to.

Everything below is justified against this one sentence: if a permission does not serve holding/moving assets or signing for a connected dApp, it should not be in the manifest.

## 2. Permission justifications

One paragraph per permission, written for the reviewer who reads the CWS permission-justification field: what it does, why the single purpose above requires it, and what it explicitly does not do. These mirror `docs/Privacy_Policy.md`'s "Permissions and what they are used for" section; the two must stay in sync; a reviewer who reads both fields against each other is exactly the failure mode this file exists to avoid.

**`storage`**  
The wallet stores your encrypted seed and keys, your addresses and settings, and the list of dApp origins you've approved, all in `chrome.storage.local`, entirely on your device. The single purpose requires persisting a self-custodial wallet across browser restarts; without `storage` the wallet could not remember your accounts or your dApp approvals between sessions. It is not used for analytics, tracking, or any data that leaves the device.

**`sidePanel`**  
Lets the user open the wallet in the browser's side panel as an alternative to the toolbar popup, so the wallet UI can stay visible next to the page being used. It shows and operates on exactly the same on-device wallet state as the popup; it is a second UI surface for the same single purpose, not a new capability or a new data source.

**`notifications`**  
Delivers a native browser notification for a background wallet event the user configured (a price alert, a governance-poll update, a payment deadline, a dispenser-escrow event) so the user sees it even when the popup is closed. This directly serves "moving assets": several of these events are time-sensitive and the wallet has no server component to push through instead. Notification content is generated on-device from data already on-device; nothing about the notification is sent anywhere.

**`alarms`**  
Chrome shuts down an idle Manifest V3 service worker after roughly 30 seconds. `alarms` schedules a wake-up roughly every 24 seconds so the wallet's background worker, and the watchers described above (price/notification polling, the auto-lock timer), keep running. Without it, background notifications and the auto-lock safety timer would silently stop working between user interactions. It is purely a scheduling primitive; it collects and transmits nothing itself.

**Content script (`https://*/*`, `http://localhost/*`, `http://127.0.0.1/*`)**  
See section 3 below; justified together with the injected provider since they are one mechanism.

**`web_accessible_resources`**  
Exposes two static asset sets to pages that request them: the injected provider bundle (`inject/xchainProvider.js`), which is the file the content script loads to give a page `window.xchain`, and a set of chain-icon images (`chain-icons/*`) that a connected dApp can use to render a recognizable icon for the coin it's dealing with. Both are read-only static files shipped in the extension bundle; neither carries wallet data, and neither is writable by the page.

## 3. Content script and injected-provider justification

Paste into the CWS field that asks about the content-script / all-sites justification:

> XChain Wallet is a browser-extension crypto wallet in the same family as MetaMask and similar wallets: any website can be a "dApp" that wants to request a connection, so the content script runs on secure origins (`https://*/*`) to inject a `window.xchain` provider object that a page's own script can call. It additionally runs on `http://localhost/*` and `http://127.0.0.1/*` so that developers building against the wallet can test on a local server. It deliberately does NOT run on other plain-HTTP origins: on a page served without TLS an on-path attacker can rewrite the page and impersonate the dApp, so the wallet declines to offer a provider there at all rather than relying on the user to notice.
>
> The provider does not read page content. It only relays requests a page's script explicitly makes to it (account address requests, transaction/action signing requests) to the wallet's background service worker over an isolated message channel, and relays the wallet's response back.
>
> No page gets anything from a connected wallet without the user approving that specific site first. This is the extension's ConnectedSites model: the first time a page calls the provider, the wallet shows a connection-approval prompt naming the requesting origin; only origins the user has approved receive account data or signing prompts, and the user can revoke a site's approval at any time from the wallet's settings. Injection alone (the content script running, the provider object existing on the page) grants a page nothing: it establishes a channel, not access.

## 4. Listing copy

**Verified 2026-07-31 (stage S7)** against the current build (`pnpm --filter @xchain-wallet/extension build`, driven live via `packages/extension/scripts/capture-listing-screenshots.mjs`) and against `packages/extension/src`:

- The 132-character summary was counted with `node -e` at submission time and measures **124 characters**, within the 132 limit.
- Every feature claim in the description was checked against the shipped code, not assumed: side panel (`sidePanel` permission + `sidepanel.html`, confirmed live in this stage's own screenshot), per-site connect approval (`requireSite` gate in `packages/extension/src/bridge/handlers.js`), plain-language review before signing (`SignApproval.jsx`'s `PsbtIntentPanel` / `ActionIntentSummary`; the raw hex view is developer-mode-only), and signer support. Signer support in particular: `packages/extension/src/signers/` contains only `ledgerFactory.js`, and `App.jsx`'s own comment says it plainly ("Trezor is intentionally NOT offered in the extension shell... the extension ships Ledger (WebHID) + software signing only"). The description already said exactly that ("a software-derived key or a paired Ledger hardware wallet") and makes no Trezor claim, so it needed no correction here; `docs/Privacy_Policy.md` carries the same Trezor-exclusion language (§3.3's fix, stage S1).
- The "no accounts, no analytics, no tracking" line was checked against `docs/Privacy_Policy.md`'s own "Third parties" section (no analytics/advertising/attribution/crash-reporting SDK, no first-party server) and is consistent with it; the description defers detail to the policy rather than re-stating the policy's own toggleable third-party contacts (price data, token metadata, explorer favicons), so the two documents cannot go out of sync on that point.

The summary and description text below are therefore final as written, pending only D2 (name/category, spec §8, not yet decided by the operator - see the Name row below).

**Name:** XChain Wallet (working title; final confirmation is spec §8 D2, an operator decision this stage does not make)

**132-character summary (124 characters, limit 132):**

> Self-custodial wallet for Bitcoin, Dogecoin, Litecoin, and XChain assets. Connect to dApps and sign right from your browser.

**Full description (plain language per wallet docs voice):**

> XChain Wallet is a self-custodial browser wallet for Bitcoin, Dogecoin, Litecoin, and the tokens issued on the XChain Platform. "Self-custodial" means your keys stay on your device: XChain Wallet never sees your seed phrase, never holds your funds, and there is no account to lose access to.
>
> With XChain Wallet you can:
>
> - Hold and send Bitcoin, Dogecoin, Litecoin, and XChain-issued tokens
> - Connect to XChain dApps from your browser, one site at a time, with your explicit approval before any site can see an address or ask for a signature
> - Sign with a software-derived key or a paired Ledger hardware wallet
> - Review every transaction before you approve it, in plain language, not raw hex
> - Use the side panel to keep your wallet visible while you browse
>
> XChain Wallet stores nothing about you on a server because it doesn't have one: no accounts, no analytics, no tracking. See the privacy policy for the full detail on what stays on your device and what leaves it (and why).
