# tools/release/expected-artifacts.txt - the artifact set a release must contain.
#
#  §6. Read by tools/release/lib.sh (xr_check_expected), enforced by
# sign.sh before it writes a manifest.
#
# WHY THIS FILE EXISTS. sign.sh hashes whatever it finds. Without a
# declared set, a staging directory holding three of nine artifacts
# produces a manifest that is internally perfect - every hash correct,
# signature good, verify.sh green - and describes a release that was
# never built. The gate runs in both directions:
#
#   required   at least one artifact must match, or signing fails.
#              This is what catches a shell that did not build.
#   optional   allowed to be present, never demanded.
#
#   Anything in the staging directory matching NO line below is a hard
#   failure. That is what catches a leftover from the previous version,
#   a stray build output, or a file someone else put there.
#
# Channel pointers never appear here: they are electron-updater's mutable
# update-info files and are excluded from the manifest entirely (lib.sh).
# They are identified by CONTENT, not by name - our channel is `stable`,
# so the real names are `stable.yml` / `stable-mac.yml` / `stable-linux.yml`
# / `stable-linux-arm64.yml`, and the old `latest*.yml` glob matched none
# of them ( §7.1).
#
# Blockmaps (`*.blockmap`) are deliberately absent, so staging one is a
# hard failure. Differential updates are a non-goal ( §7); a
# blockmap in the release directory means the desktop build emitted
# delta metadata that would be served but never verified.
#
# WHEN THE ARTIFACT SET CHANGES, this file changes in the SAME commit.
# A stale list either blocks a legitimate release or, worse, silently
# stops demanding a shell that quietly dropped out of the build.
#
# THE THIRD COLUMN IS THE BUILD PROFILE (, rails §3): which set of
# features was compiled into that artifact. `default` is the full app
# (web, desktop, extension); `store` is the mobile store build, which
# compiles OUT the surfaces the app-store review posture hides (
# §2.3). Two artifacts of one tag can hold different code, so the profile
# is written into the signed manifest and every declared glob must name
# one. A missing or unknown profile fails the gate here, at declaration
# time, rather than when a release is already staged.
#
# The direct APK is `store` and that is not a typo:  §6 derives it
# from the same AAB, so it is the store build's code signed by a
# different key. Anything compiled out for review is therefore also
# absent from the direct download.
#
# THAT COUPLING IS NOW A CHOICE RATHER THAN A CONSEQUENCE (operator answer
# to , 2026-08-07). A SECOND direct APK is declared below at the
# `default` profile, so the audience that deliberately avoids Play can get
# the full feature set. The store-derived APK above stays exactly as it is:
# it is what Play's review posture permits, it is derived from the uploaded
# bundle, and it remains the file the download page offers by default.
#
# THE FOURTH COLUMN IS THE ARCHITECTURE SET, and it exists because this
# file's globs are extension-shaped: `*.dmg` is satisfied by ONE dmg. On
# 2026-08-01 every desktop lane turned out to be building one architecture
# instead of two (a `--` that ended electron-builder's option parsing,
#  §8) and this gate passed the resulting release without a word:
# arm64 users would have had no download, no update, and no channel
# pointer, and the manifest covering that release would have been
# internally perfect. Each required arch must now be present, matched
# against the artifact NAME using electron-builder's own arch tokens
# (`-x64`, `-arm64`, `_amd64`, `x86_64`). Since §7.1's rename EVERY
# artifactName is user-forced, so there is no un-suffixed artifact left to
# make an exception for: an AppImage without a token means the forced name
# was lost, and lib.sh refuses it rather than guessing x64.
#
#   -            not arch-partitioned: one artifact serves everyone.
#   x64,arm64    both must be present, or the release fails here.
#   multi        ALLOWANCE, never a requirement: tolerate one artifact
#                that carries several arches and therefore has no token.
#                Not declared anywhere today on purpose - the combined
#                NSIS installer is 's open question, and until it
#                is answered the gate refuses the release rather than
#                publishing a third installer nobody chose.
#
# An artifact that matches an arch-partitioned row and carries NO token is
# a hard failure, not a default-arch guess: a combined installer and a
# broken artifactName look identical from here, and both deserve an answer.
#
# THE FIFTH COLUMN IS THE SIGNATURE CLASS , and it exists because
# this gate counted artifacts and architectures and never once asked
# whether any of them was SIGNED. Windows signing is selected off three
# environment variables and electron-builder.config.cjs says in as many
# words that with them unset it "is entirely inert ... still produces
# unsigned artifacts"; macOS skips signing with a warning. So ONE missing
# repository secret yields a complete, correctly-named, two-architecture
# set of UNSIGNED installers, which this gate passed without comment and
# sign.sh then hashed into a K1-signed manifest. K1 attests the BYTES, not
# the publisher, so that manifest verifies perfectly over an unsigned
# release. Same family as the arch column above: a declared class that is
# never counted.
#
# It matters beyond one bad release. An unsigned build shows the "unknown
# developer" warning  records as an explicit operator requirement
# not to have, and electron-updater refuses an update whose signed
# publisher does not match the installed app's - `WIN_PUBLISHER` is called
# "effectively a wire format" in the build config - so shipping unsigned
# can strand the fleet that already installed signed.
#
#   authenticode             we sign it; the PE certificate table is read
#   codesign                 we sign it; the sealed _CodeSignature is read
#   none                     genuinely unsigned by design (Linux has no OS
#                            signature for a generic binary; the web
#                            tarball and extension zip are not OS
#                            artifacts). Integrity rides the K1 manifest.
#   store                    the receiving store signs it after upload, so
#                            what we stage is legitimately unsigned
#   codesign-dmg             the disk image itself, signed AND notarized;
#                            assessed with spctl the way Gatekeeper
#                            assesses a download ( row 140). It
#                            replaced `codesign-unverified`, which had
#                            declared the dmg Apple-signed and skipped the
#                            check on that basis, while the published dmg
#                            was not signed at all
#   authenticode-unverified  the signed PE is inside the archive; the .exe
#                            row covers the same lane
#   deferred-android         apksigner's lane , declared not checked
#
# THE UNVERIFIED CLASSES ARE STATED GAPS, NOT EXEMPTIONS. The checker
# reports them as `recorded` and never as `ok`, and prints the two counts
# separately, because "we did not look" and "we looked and it was fine"
# being indistinguishable is the exact hole the column was added to close.
#
# A row with a MISSING or misspelled class is a hard failure. lib.sh reads
# only four columns (`status pattern profile arches _rest`), so a fifth
# column is discarded there without a word - meaning nothing in bash can
# notice an ungated row. tools/release/verify-signatures.mjs validates the
# declaration itself, at parse time, before it looks at any artifact.
#
# THE FIRST COLUMN ALSO NAMES THE RELEASE SET ( §7.5, ).
#
# AND, ON A STAGING ROW, THE OS THAT ROW BELONGS TO (operator answer, §7.5,
# 2026-08-07). A rehearsal is per-OS - §7.5 says to watch a swap complete
# "on at least one OS" and to emit variants "on the arches being rehearsed" -
# but the gate used to demand every staging row at once, so a Linux-only
# rehearsal failed on the mac and windows rows and the first rehearsal this
# project could run was one that needed the Apple and Azure credentials the
# rehearsal exists to de-risk. Spelling the OS into the status token keeps
# ONE file and one parse: `xr_set_for_status` returns nothing for a token it
# does not recognise, and an unrecognised status is already a hard failure,
# so a misspelled or ungated OS cannot slip through the way a discarded
# sixth column would (see the four-column warning above).
#
# `sign.sh --staging --os linux` then gates against the linux rows only and
# writes `# rehearsal-os: linux` into the signed header, so a scoped
# rehearsal manifest says what it covers instead of leaving a reader to
# infer it from which files are listed. A bare `--staging` still demands
# every staging row, which is the whole-set rehearsal a full release cuts.
#
# `required`/`optional` describe a PRODUCTION release. `staging-<os>-required`/
# `staging-<os>-optional` describe the §7.5 rehearsal set, which exists so the
# update path can be exercised against a staging feed before anything is
# published. `xr_check_expected` takes the set as its third argument and
# skips every row belonging to another one, so the two shapes cannot
# satisfy each other in either direction.
#
# WHY THE REHEARSAL SET NEEDED ITS OWN SHAPE AT ALL. A staging build
# deliberately emits ONLY the update-capable formats - mac zip, win nsis,
# linux AppImage and deb - because a staging variant of a format with no
# auto-update path exercises nothing. So it can never contain the web
# tarball, the extension zip, the dmg or the mobile artifacts, and the
# production rows below can never be satisfied by it. Until 2026-08-07
# that meant the rehearsal set could not be signed at all: `sign.sh` ran
# the production gate over it and refused with 14 problems, while
# release.yml's own ceremony summary instructed the operator to sign it
# and §7.5 recorded an operator decision that K1 signs it. The rule, the
# instruction and the tool disagreed, and the tool won every time, which
# is why the live rehearsal had never once run.
#
# WHY NOT THE PROFILE COLUMN, which is the obvious place. A staging
# AppImage is built by the `default` profile - the same code with a
# different feed URL baked in - so that column already says something
# true about it. Overloading it would also break `xr_profile_for`, which
# refuses when one filename matches two globs declaring DIFFERENT
# profiles. Splitting on status keeps both shapes in this one file where
# they can be read against each other, and leaves that function correct
# with no change.
#
# THE ARCH AND SIGNATURE COLUMNS STILL MEAN WHAT THEY MEAN on a staging
# row. The rehearsal is per-arch for the same reason the release is: a
# rehearsal that exercised one arch would prove nothing about the other.
#
# Format:  <required|optional|staging-required|staging-optional>  <glob>  <profile>  <arches>  <signature class>

# --- Web SPA ------------------------------------------------------------
required  xchain-wallet-web-v*.tar.gz       default  -         none
# --- Chrome extension ---------------------------------------------------
# The store zip. What the Chrome Web Store returns to users is a
# store-signed CRX repacked from this, so the manifest proves what was
# submitted, not what was delivered (§3,
# https://docs.xchain.io/components/wallet/release/verify-release).
required  xchain-wallet-extension-v*.zip    default  -         none
# --- Desktop (electron-builder) -----------------------------------------
# Extension globs rather than exact names. They used to be necessary
# because electron-builder embedded productName ("XChain Wallet", with a
# SPACE) in every artifact; since §7.1's rename every name is pinned to
# `xchain-wallet-...` and no published file has a space in it.
#
# The per-arch naming convention this used to defer to  for is now
# SET: every macOS and Windows artifact carries its architecture
# ("-x64" / "-arm64"), because electron-updater selects an artifact by
# substring-matching `process.arch` against the filename. That is an
# update-correctness rule, not a cosmetic one; see the DD4 block in
# packages/desktop/electron-builder.config.cjs.
#
# The globs stay extension-based, but the ARCH COLUMN is now what makes
# them mean something. It used to say here that extension globs meant
# adding an arch would not require editing this file; that was true and it
# was the bug - a lane could DROP an arch without editing this file
# either. Adding a seventh lane (armv7l, DD1) now edits one column, and a
# lane that quietly stops building does not get to pass.
#
# All three OS families are required. "One release = all shipped shells"
# (§2): a tag that produced only the artifacts the release machine could
# build natively is exactly the version skew this gate exists to refuse.
# Satisfying the Windows and macOS rows needs the §5 CI matrix (S4).
required  *.dmg                             default  x64,arm64 codesign-dmg
required  *mac*.zip                         default  x64,arm64 codesign
#
# EXACTLY TWO WINDOWS INSTALLERS, one per arch (, operator decision
# 2026-08-01). electron-builder's default ALSO emits an un-suffixed
# installer carrying both architectures, ~193M against ~113M and ~96M;
# `nsis.buildUniversalInstaller: false` stops it being produced at all.
#
# No `multi` here, deliberately. That token would tell this gate an
# un-suffixed installer is expected, and it is not: if one appears, the
# suppression flag has been lost and the release should fail loudly rather
# than put a third installer on the feed and a third choice on the
# download page. The config is the mechanism; this row is the backstop.
required  *.exe                             default  x64,arm64 authenticode
required  *win*.zip                         default  x64,arm64 authenticode-unverified
required  *.AppImage                        default  x64,arm64 none
required  *.deb                             default  x64,arm64 none
# --- Mobile -------------------------------------------------------------
# Optional, not required, so a release today does not demand them - but
# declared, so the day one is staged it is covered by the manifest instead
# of hard-failing as undeclared.
#
# The Android pair is NOT two builds and NOT the same lane ( §6):
# the ceremony builds ONE AAB and derives the universal APK from that same
# bundle, so the two files are the same code signed by different keys.
#
#   .aab   store-bound, signed by K9, uploaded to Play, NEVER hosted
#          publicly. Hashed into the manifest anyway: the manifest is the
#          record of what was submitted, since Play re-signs and serves
#          device-split APKs that cannot be verified against it at all.
#   .apk   the DIRECT download, signed by K10, hosted on
#          downloads.xchain.io. This is the only verifiable Android
#          artifact, and the one users check by hand
#          (`apksigner verify --print-certs`), so it is the one whose
#          absence from a manifest would matter most.
#
# iOS stays store-bound-only: there is no direct-install lane on that
# platform to have a second artifact for .
#
# All four mobile/store rows are arch-agnostic here. The Android pair is
# universal by construction (one AAB, one derived universal APK) and the
# .ipa is a single fat archive. The `-mas.pkg` used to be the one that
# could be either. DECIDED 2026-08-07 by the operator and written here,
# which is where this comment always said it would go: the store package is
# UNIVERSAL. It is a constraint before it is a preference, because an App
# Store version carries exactly one build, so a per-arch pair is two
# candidates for one slot rather than something the store can serve.
optional  xchain-wallet-android-v*.aab      store    -         deferred-android
optional  xchain-wallet-v*[0-9].apk         store    -         deferred-android
#
# THE SECOND DIRECT APK: same tag, `default` profile, K10 signature, and it
# exists because  was answered `build it` rather than `document the
# coupling`. The `store` profile genuinely compiles the DEX lane out (eight
# modules) along with the Trezor connect CSP origin, so until this row the
# users who avoid Play on principle were getting Play's restrictions anyway.
#
# WHY THE ROW ABOVE IS ANCHORED `*[0-9].apk`, WHICH LOOKS LIKE FUSS AND IS
# NOT. `xchain-wallet-v*.apk` is GREEDY: measured 2026-08-07 against the real
# `xr_profile_for`, a default-profile APK named the obvious way did NOT fail
# the gate. It resolved to `store`, silently, because both names matched one
# glob declaring one profile, so there was nothing ambiguous to report. That
# writes a FALSE profile into a signed, append-only manifest - a verifier
# reads `store` as "the review-hidden surfaces are absent" from the one build
# that still contains them, which is precisely what
# `xr_assert_store_profile_buildable` exists to make impossible, arriving
# through the filename instead of the status file.
#
# Anchoring the store row to a trailing DIGIT and suffixing this one makes
# the two globs disjoint by construction rather than by care: a released
# name ends in its version, this one ends in `-full`, and any OTHER suffixed
# APK now matches NEITHER row and fails shut as undeclared instead of
# inheriting `store`. Fail-shut is the correct answer for a name nobody
# planned - the whole defect above was a name nobody planned being silently
# given a meaning.
#
# `deferred-android` like its twin: apksigner's lane, declared not checked.
# Optional, and its lane is NOT-SHIPPED in shipped-lanes.txt, so nothing
# demands it until the first ceremony actually produces one.
optional  xchain-wallet-v*-full.apk         default  -         deferred-android
optional  xchain-wallet-ios-v*.ipa          store    -         store
optional  *-mas.pkg                         store    universal store
#
# The Microsoft Store package ( §15). Optional for the same reason
# as `-mas.pkg`: the channel is a goal, the Partner Center identity does
# not exist yet, and the lane is opt-in behind XCHAIN_BUILD_APPX=1.
#
# It IS arch-partitioned, unlike the mac store row, and the difference is
# real rather than a guess: the Store serves an architecture-specific
# package to each device, and `appx.artifactName` carries `${arch}`, so a
# release that staged one arch of the store package would ship half the
# Windows fleet. Declared x64,arm64 - if the Store lane ever produces a
# single bundle instead, this column is where that gets written down.
optional  *-appx.appx                       default  x64,arm64 store
#
# The Snap Store package ( §16, ). Optional for the same
# reason as the two rows above: the channel is a goal, the Snapcraft store
# account does not exist yet, and the lane is opt-in behind
# XCHAIN_BUILD_SNAP=1. Hashed into the manifest like the .aab: the store
# serves it under its own assertions, but the manifest records what was
# uploaded.
#
# Arch-partitioned like appx: the store serves a per-arch snap, and the
# pinned artifactName carries `${arch}` in snapcraft's Debian-style
# spelling (`_amd64`/`_arm64`), which lib.sh already attributes.
optional  *.snap                            default  x64,arm64 store

# --- The §7.5 rehearsal set ---------------------------------------------
#
# The update-capable formats, and ONLY those, per OS. This is the same
# list `UPDATE_CAPABLE_TARGET` builds in electron-builder.config.cjs, and
# the two must be changed together: a format added there and not here is
# an artifact the gate will refuse as undeclared, and a format added here
# and not there is one the gate will demand and never receive.
#
# The dmg and the win zip are deliberately ABSENT rather than optional -
# neither has an auto-update path, so a staging variant of either
# exercises nothing and staging one means something went wrong in the
# build. Same for the web tarball, the extension zip and every mobile
# artifact: those lanes do not update through this feed at all.
#
# Signature classes are inherited from the production rows rather than
# relaxed. A rehearsal is meant to exercise the REAL update path, and
# electron-updater refuses an update whose signed publisher does not
# match the installed app's - so an unsigned staging mac zip or nsis
# installer would fail in the rehearsal exactly as it would in
# production, which is the point.
staging-mac-required      *mac*.zip                 default  x64,arm64 codesign
staging-windows-required  *.exe                     default  x64,arm64 authenticode
staging-linux-required    *.AppImage                default  x64,arm64 none
staging-linux-required    *.deb                     default  x64,arm64 none
