# tools/release/shipped-lanes.txt - which distribution lanes have shipped,
# and therefore may never silently drop out of a release again.
#
# §6 ("never let the direct lane lag the Play lane in RELEASE
# PARITY"), §2 ("one release = all shipped shells"). Read by
# tools/release/lib.sh (xr_check_shipped_lanes), enforced by sign.sh
# alongside the expected-artifacts gate.
#
# WHY THIS FILE EXISTS, and it is a different question from the one
# expected-artifacts.txt answers.
#
# That file has exactly two strengths per row: `required` (every release
# must contain it) and `optional` (a release may contain it, and is
# covered by the manifest when it does). Every store lane starts optional
# and has to, because a lane that has never shipped cannot be demanded of
# a release built before it existed.
#
# The trap is what happens on the day it DOES ship. Nothing about the
# first upload edits expected-artifacts.txt. So the release after the
# first Android release could omit the Android pair entirely and produce
# a manifest that is internally perfect - every hash correct, signature
# good, verify.sh green - describing a release that left every direct
# APK install without the fix it was told to expect. That is the same
# shape of defect as the §8 missing-architecture gap, one level up: the
# gate cannot fail on an artifact it was never told to want.
#
# So the lane's shipping state is DECLARED here, once, and the gate reads
# it. Flipping one word is what arms the parity requirement, and the
# store submission runbooks name that flip as a step of the first release
# rather than leaving it to be remembered.
#
# FAIL-SHUT, in both directions:
#
#   * A lane row with any status other than SHIPPED or NOT-SHIPPED is a
#     hard failure at parse time, not a default to the permissive one.
#   * A glob here that appears in no expected-artifacts.txt row is a hard
#     failure: the two files would be describing different releases.
#   * An `optional` row in expected-artifacts.txt claimed by NO lane here
#     is a hard failure. That is what stops a future optional artifact
#     from being added with no shipping state at all, which would put it
#     straight back in the hole this file was dug to fill.
#
# Nothing here demands anything of a NOT-SHIPPED lane. Staging its
# artifacts early is still allowed and still covered by the manifest;
# expected-artifacts.txt is what permits that, and this file does not
# take it away.
#
# WHEN A LANE SHIPS: flip its word to SHIPPED in the SAME commit that
# records the release, and say in the comment which tag it first shipped
# in. From then on a release that omits it fails here, by name.
#
# Format:  <lane>  <SHIPPED|NOT-SHIPPED>  <glob> [<glob> ...]
#          globs are matched against artifact basenames, exactly as in
#          expected-artifacts.txt, and must be declared there too.

# Android. The pair is ONE build: the ceremony signs the AAB with
# K9 and derives the universal APK from that same bundle with K10, so a
# release carrying one and not the other means the ceremony was
# interrupted, never that only one lane was intended. They flip together.
#
# SHIPPED in v0.336.0, published 2026-08-06 to
# downloads.xchain.io/wallet/android/xchain-wallet-v0.336.0.apk and attested
# by the signed partial manifest at RELEASE_HASHES/v0.336.0.txt. Verified
# after upload by fetching both from the public URL and re-running verify.sh
# against them: hashes match, the header anchors to v0.336.0, and the GPG
# signature is good.
#
# The DIRECT half is what shipped. Play has never distributed this app, and
# the lane
# flips on the direct half deliberately: §6 says the direct lane never waits
# on a Play clock, so the parity requirement it arms is the one that matters
# to the users who can actually install this. The .aab glob stays in the row
# because the pair is one build: the ceremony derives the APK from the same
# bundle it signs as the AAB, so a release carrying one without the other
# means the ceremony was interrupted.
#
# The APK glob is ANCHORED to a trailing digit, and the reason lives in
# expected-artifacts.txt beside the row it guards: `xchain-wallet-v*.apk`
# also swallowed the full-feature APK below, silently labelling it `store`.
# This row must keep spelling the glob exactly as that file does, because a
# glob here that no row there declares is a hard failure by design.
android   SHIPPED       xchain-wallet-android-v*.aab xchain-wallet-v*[0-9].apk

# The second direct APK (operator answer 2026-08-07): the same tag
# built at the `default` profile and signed by K10, for the audience that
# avoids Play deliberately and has been getting Play's restrictions anyway.
#
# ITS OWN LANE RATHER THAN A THIRD GLOB ON THE ANDROID ROW, and that is the
# whole reason this could land before the artifact exists. The android row is
# SHIPPED, so every glob on it is DEMANDED of every release from now on:
# adding this one there would make `android SHIPPED` require an artifact
# nothing builds yet, failing every release until a ceremony with the K9/K10
# keystores and a real Android toolchain had run. A separate NOT-SHIPPED lane
# claims the glob - so the optional row is not an unclaimed artifact, which is
# also a hard failure here - while demanding nothing, exactly like the four
# store lanes below.
#
# The ceremony leg that builds it is opt-in behind XCHAIN_BUILD_ANDROID_FULL=1
# for the same reason. Flip this to SHIPPED in the commit that records the
# first release actually carrying the file, and from then on a release that
# omits it is a lane left behind rather than a smaller release.
android-full NOT-SHIPPED xchain-wallet-v*-full.apk

# iOS. Store-bound only; there is no direct-install lane on that
# platform, so this row is one glob and always will be.
ios       NOT-SHIPPED   xchain-wallet-ios-v*.ipa

# Mac App Store. Blocked on Apple Developer Program enrollment
# and the distribution certificates that follow it.
mas       NOT-SHIPPED   *-mas.pkg

# Microsoft Store (§15). Opt-in behind
# XCHAIN_BUILD_APPX=1 and the Partner Center identity does not exist yet.
msstore   NOT-SHIPPED   *-appx.appx

# Snap Store (§16). Opt-in behind XCHAIN_BUILD_SNAP=1 and
# the Snapcraft store account does not exist yet (ceremony: account +
# reserved name + exported login). Flip to SHIPPED in the commit that
# records the first store upload.
snap      NOT-SHIPPED   *.snap

# Chrome Web Store. THE ODD ONE OUT, and the reason it belongs
# here is worth stating, because the shape of every other row above is
# "an artifact nothing else builds".
#
# The extension zip is `required` in expected-artifacts.txt and is built
# by the same CI run as the web tarball and the desktop installers, so it
# never had a lane: it could not go missing from a release without the
# artifact-set gate saying so, which is what a lane row exists to catch.
#
# What it shares with the rows above is the other half: it is uploaded to
# a STORE, on its own schedule, and until 2026-08-06 that upload was held
# hostage by a credential belonging to a different lane. `sign.sh` signs a
# release as a set, two Windows installers in that set were unsigned for
# want of an Azure Trusted Signing account, and so the Chrome submission
# could not have a signed manifest at all - not for any reason inside the
# Chrome ceremony, and not for anything the extension zip itself lacked.
# This row is what lets `sign.sh --lane extension` attest the one artifact
# the store is actually getting (operator decision 2026-08-06).
#
# NOT-SHIPPED until the first upload clears review, exactly like the rows
# above: flip it to SHIPPED in the commit that records that upload in
# packages/extension/docs/publish-log.md, and from then on a release that
# stages no extension zip is a lane left behind rather than a smaller
# release. The signature class of its glob is `none`, so a partial
# manifest scoped to this lane demands no OS code signature; Chrome signs
# the item itself, with a key the store holds and we never see.
extension NOT-SHIPPED   xchain-wallet-extension-v*.zip
