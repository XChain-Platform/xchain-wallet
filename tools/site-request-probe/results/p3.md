## P3: long launch and return URLs

Run on 2026-11-22 on the Mac host (macOS 27.2.1, Node 22.23.4), a Linux host
over ssh, an Android emulator and an iPhone simulator. Every URL was built by
one deterministic generator to exactly the stated total length, scheme and
prefix included, from ASCII base64url characters, so characters, UTF-16 units
and UTF-8 bytes are equal. Each receiver printed only the received length and
the SHA-256 of what it received; `INTACT` means both equal the sender's.
16,384 (`URI_MAX_LENGTH`) was added to every leg beside 2,000, 8,000 and
16,000. Launch shape: `...?uri=<payload>`. Return shape:
`...#xchain=<payload>`, so the fragment is carried too.

The probe scripts and capture apps lived in an ignored scratch directory
(`tmp/p3-claude/`) and are not committed. Earlier codec, model and
physical-device rows were dropped; nothing below comes from a model.

The receivers were small capture apps (an Android APK, an iOS simulator app,
a macOS URL handler app) and a loopback page server, not the wallet's own
Android, iOS or desktop builds. The wallet's current 4,096-character intake
guards (below) would have refused the longer URLs, so P3 measures the
transports, not today's wallet intake.

### Classification of the one cut

`xcrun simctl openurl` delivered exactly the first 2,047 characters of every
URL longer than that (the received hash equals the SHA-256 of the sender's
first 2,047 characters, for example `0da92c5c...` for the 16,000-char launch
URL), and Safari's request target was 2,025 characters (2,047 minus the
22-char `http://127.0.0.1:47613` origin). The cut is in the simulator host
bridge that `simctl openurl` uses, not in iOS or Safari: the same Safari on
the same simulator received all 16,384 characters by in-page navigation, and
by `UIApplication.shared.open` from an app, which goes through the device's
own LaunchServices. It is a probe-tool limit and does not move the cap, but
it means `simctl openurl` cannot be used to test links over 2,047 characters.

### Not run, and why

- Windows argv: there is no Windows host in this setup, so nothing was
  executed. Reference only, not a measurement: `CreateProcess` documents a
  32,767-character limit for `lpCommandLine`, which includes the executable
  path, quotes and spaces, so a 16,384-char URL argument fits with room to
  spare. A launch through a registered protocol handler passes through the
  Windows shell before `CreateProcess`; that path is also unmeasured and
  needs its own Windows run before release.  
- iOS Universal Link to an app: an app-routed Universal Link needs an
  `apple-app-site-association` file on the claimed domain naming the app's
  team and bundle id. An ad-hoc signed capture app cannot be associated with
  a real domain, so no link was routed by association. The URL delivery
  paths around it (Safari, `UIApplication.open`, app `open url`) were run.  
- Android implicit https `ACTION_VIEW`: with no verified App Link the intent
  matched more than one activity, and `am start -S` refused at every length,
  2,000 included, with
  `Error: Intent matches multiple activities; can't stop: Intent { act=android.intent.action.VIEW dat=https://xchain.io/... }`.
  This is resolution, not length. A browser-driven `intent://` wrapper was
  not run.  
- Electron `shell.openExternal` into a web browser: the https return was
  measured into a registered `xchainp3:` handler app standing in for the
  browser, so no tabs were opened in the operator's browser. The
  Electron-to-LaunchServices-to-handler path is measured; a browser's own
  handling of a long incoming URL is not.
